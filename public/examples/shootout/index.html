Programming language shootout.

Ten problems, two styles, and the choices behind the measurements.

Run the checksSuite guideRecorded results

Recorded on an Apple M4 Max, 12 November 2026 UTC. Local inputs, twelve x2c samples; foreign results use an earlier calibration. These are local comparisons, not published Benchmarks Game results.

A small numerical loop and a DNA-processing pipeline ask different things of a language. One spends its time on arithmetic. Another creates strings, looks up keys, and moves bytes between buffers. A single score hides those differences.

This experiment starts with ten Computer Language Benchmarks Game problems. Each has two x2c implementations: an idiomatic version built with ordinary collections and APIs, and a tuned version that specializes the work where it matters. The question is what changes when we move between those styles, and how much code that change needs.

In the recorded November 2026 local-input snapshot, across the eight problems shared by all eight implementation columns, tuned x2c takes 1.20 times the C elapsed time, with 0.89 times the C source lines. Those are geometric means of matched problem ratios. The individual programs tell a more useful story than that summary.

Start with the individual problems

Tuning makes its largest differences in the text-processing programs. On k-nucleotide, elapsed time falls from 102.8 ms to 17.4 ms. FASTA falls from 22.6 ms to 4.4 ms, and reverse-complement from 12.4 ms to 2.5 ms. Each pair solves the same problem specification, but changes how the program represents or moves its data.

Other pairs barely move. The two binary-trees sources are identical; their 26.6 ms and 26.8 ms medians are separate measurements of that same source. Pi digits also changes little: 281.5 ms becomes 269.2 ms. There is no single transformation that explains every row.

These are small local inputs. Mandelbrot's C baseline is 2.8 ms, while pi digits takes 263.4 ms. A ratio should be read with its absolute time; it does not tell us how much time a larger application would save.

Put the representation where the work is

The n-body simulation keeps five bodies moving under mutual gravity. The idiomatic implementation uses heap objects and an Array of body pairs. The tuned version keeps the five bodies in a native array of structs and visits each pair with two loops. It still uses Vec3 methods and required reference parameters for the physics.

On this input, n-body goes from 72.9 ms in 102 source lines to 33.2 ms in 82 lines. The C program takes 32.8 ms. Here, making the fixed shape explicit also removes code: the tuned program does not need a separate collection of pair objects.

K-nucleotide makes a different representation choice. Both implementations count all sliding windows for their requested lengths. The idiomatic program creates a String key for each window and updates a general Map. The tuned program uses MapSubInt, whose keys borrow spans of the original sequence:

MapSubInt counts = MapSubInt.new();
for (int i = 0; i + width <= sequence.len(); i++)
  counts.increment(sequence.substring(i, width));

The tuned program retains the sequence while those views are in use. It materializes strings where the frequency report needs them. This removes repeated key creation from the counting loop without replacing the required growing-map algorithm. Its 17.4 ms still exceeds the C baseline's 9.3 ms; the shorter implementation does not erase every cost.

Move bytes in batches

The idiomatic reverse-complement program reads FASTA lines, collects each sequence in a Buffer, and builds its output one line at a time. The tuned program reads 16 KiB chunks with fread, uses a complement lookup table, transforms its typed character buffer in place, and batches output before calling write_all.

That version grows from 47 to 67 source lines, while its measured time falls from 12.4 to 2.5 ms. The added code handles chunk boundaries, headers, and output buffering. It is useful code to write when this work matters; it is also more code to understand and maintain.

FASTA follows a similar route. The ordinary version builds output lines with a Buffer and stores probability choices as objects. The tuned version uses typed probability storage and a native output buffer. It grows from 65 to 82 lines and drops from 22.6 to 4.4 ms. These comparisons change several implementation details together. They do not isolate the contribution of each change.

Speed does not have one source-size cost

Tuned n-body and spectral-norm are both shorter than their idiomatic counterparts. The text-processing variants usually add code. Regex-redux grows from 61 to 97 lines: it keeps PCRE2 and independent pattern-counting threads, but uses borrowed match-data blocks instead of constructing capture Lists, plus typed buffers for substitutions. Its time falls from 26.4 to 13.3 ms.

Pi digits already delegates arbitrary-precision arithmetic to GMP in both versions. The tuned version uses fused multiply-add and multiply-subtract operations to avoid intermediate products; it retains both extracts required by the problem. This is a smaller change, and the measured difference is smaller too.

Source lines here mean nonblank lines after language-aware comment removal. They are a way to inspect the amount of source, not a measurement of clarity. The recorded dataset also includes normalized gzip bytes. On the shared cohort, tuned x2c uses 0.89 times C's source lines but 1.11 times its compressed source bytes. The answer changes with the measure.

Place the results beside the other programs

This view includes only the eight problems with an admitted contribution in every column. Tuned x2c's elapsed-time ratio is 1.20; Rust's is 1.17. Idiomatic x2c is 2.82 relative to C, with 1.19 times Python's source lines; tuned x2c uses 1.29 times Python's lines.

These are selected implementations, not rankings of what each language can do. The source choices, libraries, process model, and input sizes all matter. Java starts a fresh JVM for each sample, including startup and JIT compilation; the warmup process does not warm the next JVM. Its number is not a steady-state server measurement.

The missing contributions also matter. K-nucleotide has no admitted Rust, C++, Go, or Java entry in this environment. Binary-trees has no admitted Python entry. Those problems remain visible in the x2c comparisons above, but are excluded from the shared summary rather than silently given substitute scores.

/* Body identities stay fixed. Resolve the ten interaction pairs once. */
static Array _pairs(Array bodies) {
  Array pairs = [];
  for (int i = 0; i < bodies.len(); i++) {
    Body first = bodies[i];
    for (int j = i + 1; j < bodies.len(); j++) {
      Body second = bodies[j];
      pairs.push(Pair.new(first, second));
    }
  }
  return pairs;
}

static void Body.attract(Body body, Body other, double dt) {
  Vec3 d = body.position.sub(other.position);
  double distance = sqrt(d.dot(d));
  double magnitude = dt / (distance * distance * distance);
  body.velocity = body.velocity.add_scaled(d.scale(other.mass), -magnitude);
  other.velocity = other.velocity.add_scaled(d.scale(body.mass), magnitude);
}

static inline Vec3 Vec3.sub(Vec3 a, Vec3 b) =>
  Vec3.new(a.x - b.x, a.y - b.y, a.z - b.z);

static inline double Vec3.dot(Vec3 a, Vec3 b) =>
  a.x * b.x + a.y * b.y + a.z * b.z;

static void Body.drift(Body body, double dt) =>
  body.position = body.position.add_scaled(body.velocity, dt);

static double _energy(Array bodies) {
  double total = 0.0;
  for (int i = 0; i < bodies.len(); i++) {
    Body body = bodies[i];

      Body other = bodies[j];
      Vec3 d = body.position.sub(other.position);
      total -= body.mass * other.mass / sqrt(d.dot(d));
    }
  }
  return total;

#include <math.h>
#include <stdio.h>
#include <stdlib.h>

class Rows {
  Array input, output;
  int first, last, transpose;
  Thread worker;
} *;

int main(int argc, char **argv) {
  int n = argc > 1 ? atoi(argv[1]) : 100;
  Array u = [], v = [], scratch = [];
  for (int i = 0; i < n; i++) {
    u.push(1.0);
    v.push(0.0);
    scratch.push(0.0);
  }
  for (int i = 0; i < 10; i++) {
    _ata_times(u, v, scratch);
    _ata_times(v, u, scratch);
  }
  double uv = 0.0, vv = 0.0;
  for (int i = 0; i < n; i++) {
    uv += u[i].double() * v[i].double();
    vv += v[i].double() * v[i].double();
  }
  printf("%.9f\n", sqrt(uv / vv));
  return 0;
}

static void _ata_times(Array input, Array output, Array scratch) {
  _multiply(input, scratch, 0);
  _multiply(scratch, output, 1);
}

static void _multiply(Array input, Array output, int transpose) {
  int n = input.len(), workers = n < 6 ? n : 6;
  auto {
    if (n < 256) {
      _calculate_rows(Rows.new(input, output, 0, n, transpose));
      return;
    }
    Array batches = [];
    for (int worker = 0; worker < workers; worker++) {
      Rows rows = Rows.new(input, output,
        n * worker / workers, n * (worker + 1) / workers, transpose);
      rows.worker = Thread.start(_calculate_rows, rows);
      batches.push(rows);
    }
    foreach (Rows rows in batches) {
      rows.worker.join();
      rows.worker.free();
    }
  }
}

static void Rows.init(Rows rows, Array input, Array output,
  int first, int last, int transpose) {
  rows.input = input;
  rows.output = output;
  rows.first = first;
  rows.last = last;
  rows.transpose = transpose;
}

static Var _calculate_rows(Var input) {
  Rows rows = input;
  int n = rows.input.len();
  for (int i = rows.first; i < rows.last; i++) {
    double sum = 0.0;
    for (int j = 0; j < n; j++)
      sum += (rows.transpose ? _entry(j, i) : _entry(i, j)) *
        rows.input[j].double();
    rows.output[i] = sum;
  }
  return void;
}

static double _entry(int i, int j) =>
  1.0 / ((i + j) * (i + j + 1) / 2 + i + 1);

static void _multiply(ArrayDbl input, ArrayDbl output, int transpose) {
  int n = input.len();
  if (n < 500) {
    _rows(input, output, 0, n, transpose);
    return;
  }
  auto {
    Array jobs = [];
    for (int worker = 0; worker < 6; worker++)
      jobs.push(%!() => _rows(input, output,
        n * worker / 6, n * (worker + 1) / 6, transpose));
    Thread.run(jobs);
  }
}

static void _rows(ArrayDbl input, ArrayDbl output,
  int first, int last, int transpose) {
  int n = input.len();
  for (int i = first; i < last; i++) {
    double sum = 0.0;
    int denominator = transpose ? _entry(0, i) : _entry(i, 0);
    for (int j = 0; j < n; j++) {
      sum += (1.0 / denominator) * input[j];
      // Adjacent denominators differ by i + j + 1 (A), or i + j + 2 (At).
      denominator += i + j + 1 + transpose;
    }
    output[i] = sum;
  }
}

  regexp.jit_compile(PCRE2_JIT_COMPLETE);
  pcre2_match_data *data = regexp.native_match_data();
  PCRE2_SIZE *bounds = pcre2_get_ovector_pointer(data);
  pcre2_code *code = regexp.native();
  pcre2_match_context *context = regexp.native_match_context();
  ulong matches = 0, offset = 0;
  const char *bytes = count.sequence.bytes ? count.sequence.bytes : "";
  size_t length = count.sequence.len();

static size_t _substitute(ArrayChar sequence) {
  ArrayChar first = auto ArrayChar.new(), second = auto ArrayChar.new();
  ArrayChar current = sequence, next = first;
  foreach (List substitution in %(
    ("tHa[Nt]" "<4>")
    ("aND|caN|Ha[DS]|WaS" "<3>")
    ("a[NSt]|BY" "<2>")
    ("<[^>]*>" "|")
    ("\\|[^|][^|]*\\|" "-"))) {

    _replace(pattern, current.bytes, current.len(), replacement, next);
    current = next;
    next = next == first ? second : first;

static void _replace(
  String pattern, const char *source, size_t length, String replacement,
  ArrayChar output) {
  Regexp regexp = auto Regexp.compile(pattern, 0);
  regexp.jit_compile(PCRE2_JIT_COMPLETE);
  pcre2_match_data *data = regexp.native_match_data();
  PCRE2_SIZE *bounds = pcre2_get_ovector_pointer(data);
  pcre2_code *code = regexp.native();
  pcre2_match_context *context = regexp.native_match_context();

  output.clear();

  while ((result = pcre2_jit_match(code, (PCRE2_SPTR) bytes, length,

    raise %(bad-state (library "PCRE2") (operation "replace") (code $result));
